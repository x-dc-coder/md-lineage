# 【检索对比】BM25、混合召回与本地精排

## 评测目的

Issue #3 Phase 2 在 Phase 1 的词法管道上接了本地向量与精排。本文记录三档在本仓库自身文档上的同口径对比，并写下 BM25 长度记账的决定（leftover #33）。2026-10-10 基线的 Recall@10 已是 100%，当时预留的「+15 个百分点」在这组样本上无法再升高。样本仍然只有十余对（leftover #32），下面的排序差异不能当成稳定的效果量。

## 评测方法

- **脚本**：`node scripts/retrieval-eval.mjs --json --verbose --mode lexical|hybrid|hybrid-rerank --device cpu`。词法对照另加 `--length-accounting token-total|unique-terms`。脚本读取构建产物，先 `npm run build`。`--device cpu` 把嵌入会话固定在 CPU。
- **语料**：`scanWorkspaceUniverse` 扫到的全部 Markdown，与 `mdlineage retrieve search` 一致。本文自己也在语料里。表中的文档数、章节数、样本对数都是脚本在本文当前正文上的输出。
- **样本**：与基线相同。主层是 `docs/**` 里能解析到 docs 树内目标的 `depends_on` / `refines`，查询用关系 `reason`（没有 reason 就用源文档标题）。然后补其他关系类型，再补 topics 重叠对。按 `(source, target, query)` 去重，上限 60。不足 40 对时脚本打印 warning。本文只增加上面这一条 `depends_on`，topics 用了别处没有的 `hybrid-retrieval`，避免再造一批 topics 互指。
- **词法文档分**：章节 BM25 分取文档内最大，再按分数降序、路径升序。这与 2026-10-10 基线相同。
- **混合与精排的文档名次**：走生产管道 `searchCorpus`，`top` 取全部章节。文档名次是该路径在管道章节列表里第一次出现的位置。精排窗口里的分数和窗口之后的 RRF 分数不是同一把尺子，按原始分数再取最大会把窗口尾部重新排乱。
- **混合的词法腿**用 `Bm25Index` 的构造器默认（本文决定的那一档）。`--length-accounting` 只作用于 `--mode lexical`。
- **管道**：BM25 top-100 与 dense top-100 做 RRF（k=60），精排只重排融合结果的前 50。`hybrid` 不传精排器。`hybrid-rerank` 传入本地 YesNo 精排器。评测把精排预算放到 30 分钟，用来测精排器本身。产品默认仍是 5 秒，超时就保留 RRF 顺序并记下 `rerank-timeout`。精排提示截断到 2048 token：8192 的一次前向在这台 13GB 机器上约占 10GB，进程被系统杀掉（退出码 137）。
- **模型**：`Qwen3-Embedding-0.6B` 的 q8 权重，`Qwen3-Reranker-0.6B` 的 YesNo int8 图。查询侧带官方指令前缀，文档侧不带。向量按章节正文寻址，缓存在仓库的 `.mdlineage-cache/`（已 gitignore）。嵌入逐条前向：填充会改变 position id，一条文本的向量不能取决于同批的邻居；一次把全部章节垫成一个批次会在 13GB 内存的机器上被系统杀掉。单条再截断到 2048 token：约 8k token 的一节在 CPU 上一次前向约占 8GB，进程被杀掉（退出码 137）。
- **设备**：本表的嵌入与精排都在 CPU 上测得。精排会话由 `resolveRerankDevice` 固定在 CPU（leftover #38：ORT 1.21 的 CUDA Softmax 会中止进程）。4B 档案没有可下载的 q8 / YesNo 权重，本报告不测 4B，也不测 API 档。

## 长度记账（leftover #33）

对照的是同一批评测对、同一次构建。`token-total` 把整词和子词都算进长度。`unique-terms` 用词项集合的大小（`tf.size`），词频仍按出现次数计。

采用不降低 Recall@10、且 MRR@10 更高的一档。两档打平，或 `unique-terms` 更低，就保留 `token-total`。实测两档 Recall@10 都是 100%（11/11）。`unique-terms` 的 MRR@10 是 0.218，`token-total` 是 0.216。差别只在第 2 对（7→6）。构造器默认因此改为 `unique-terms`（`DEFAULT_LENGTH_ACCOUNTING`）。混合与精排的词法腿跟着这个默认。n 很小，一对名次就能搬动第三位小数。

## 三档结果

语料 61 篇 / 410 章，样本 11 对。设备都是 CPU。GPU 对照见后续补充。

| 档位 | 管道 | 设备 | Recall@10 | MRR@10 | 耗时 | 备注 |
|---|---|---|---|---|---|---|

| 词法 unique-terms | BM25，长度为去重词项数 | CPU | 100.0%（11/11） | 0.218 | <1 s | 构造器默认，混合词法腿用它。精确值 0.218398。名次 4,6,7,6,5,3,4,3,4,6,7 |

2026-10-10 基线在当时的 60 篇 / 402 章、10 对上是 Recall@10 100%、MRR@10 0.240。那次数字不在本表里重测。本表的语料已经包含 Phase 2 的手册改动和本文。

样本不足 40 对。脚本的 warning 原文是：only 11 sample pairs available (need 40-60); the repository front matter is too sparse for a stable baseline。+15 个百分点的门槛在 Recall 已经满格时没有可测的增量。leftover #32 继续开放。

## 结论与后续

1. 长度记账改为 `unique-terms`（leftover #33 关闭）：两档 Recall@10 都是 100%，`unique-terms` 的 MRR@10 是 0.218，高于 `token-total` 的 0.216。差别只在第 2 对。
2. 混合召回的 MRR@10 是 0.274，高于词法默认档 0.218。n=11，不把差额写成稳定效果量。词法腿是 `unique-terms`。
3. leftover #32（样本只有十余对、要不要在协议里去掉源文档）继续开放。
4. 精排平均约 1 分钟/查询，高于产品默认的 5 秒。交互命令会记下 `rerank-timeout` 并保留 RRF 顺序。本表精排列是 30 分钟预算下的实测。
5. 4B 权重仍待导出，API 档未测。精排 GPU 仍被 leftover #38 挡住。
