## 问答与研讨实录

### 问题 1：正文字节与章节内容的哈希指纹提取机制、变更逻辑与从属关系

#### 提问
> 我知道根据哈希指纹能保证我们引用的内容的唯一性，用于识别内容的身份。但是我不清楚，如何从正文字节与章节内容来提取哈希指纹？哈希指纹如何变更的？一份文档的哈希指纹和正文某章节的哈希指纹又有什么关系？

#### 回答
哈希指纹在 MDLineage 中承担着增量更新切片与内容一致性校验的核心职责：

1. **提取机制**：
   - **整篇正文哈希（Document Body Hash）**：解析器首先通过边界扫描器定位 Front Matter 的闭合标记 `---`，截取后续的正文字符串切片。将该正文字节流经由规范化处理（统一换行符并去除首尾空白）后，计算 SHA-256，生成 64 位十六进制全局指纹。
   - **章节内容哈希（Section Content Hash）**：解析器将正文编译为 Markdown 抽象语法树（mdast），遍历所有 `heading` 节点。以当前标题为起点，到下一个同级或更高优先级的标题前截止，期间包含的段落、代码块、列表等内容归属于该章节。对该章节内容独立计算 `SHA256(Title + "\n" + Section_Content)`。
2. **变更逻辑**：
   - 当文档被编辑并保存时，系统重新扫描并计算哈希值。
   - 比较旧正文哈希与新正文哈希：若两者一致，直接跳过全篇计算；若两者不一致，系统进一步比对各章节的 `Heading_Slug -> Section_Hash` 映射表，毫秒级锁定具体发生变动的章节范围。
3. **篇章哈希与章节哈希的关系（全局雪崩 vs 局部隔离）**：
   - **篇章哈希具有全局雪崩效应**：正文中任何一个小节发生修改，整篇正文的哈希必定发生改变，用于整篇文档的变更初筛；
   - **章节哈希具有局部隔离性**：某个章节的编辑不会改变其他独立章节的哈希值。系统仅标记哈希变化的小节为失效，定向触发该小节关联关系的局部重算，避免全篇盲目刷新。

### 问题 2：向量嵌入与词法倒排检索结构的开源参考与具体原理

#### 提问
> 本项目的向量嵌入与词法倒排检索结构应该是参考某个开源项目的吧？告诉我具体的原理。

#### 回答
本项目的检索架构记录于 [`open-source-landscape.md`](../project/open-source-landscape.md)，主要借鉴了三个开源项目的核心思想：
- **Microsoft GraphRAG**：借鉴其对实体、关系和主张的分层提取，以及按社区主题生成摘要的思想；
- **LightRAG**：借鉴其图拓扑结构与双轨检索的结合方式，以及轻量级增量插入流程；
- **CocoIndex**：借鉴其 Markdown 到知识图谱的数据流转换与文件增量管道。

**检索原理：混合检索（Hybrid Search）**
系统采用词法倒排与向量嵌入互补的双轨检索范式：
1. **词法倒排检索（BM25 算法）**：
   - 将 Markdown 内容切词，建立 `词项 -> 文档/章节 ID (含词频与位置)` 的倒排索引；
   - 擅长精准命中具体专有名词、API 签名、配置项键名、文档 ID 以及确切错误码（例如精确搜索 `MDL401` 或 `workspace-validator.ts`）。
2. **稠密向量嵌入检索（Dense Vector Embedding）**：
   - 将章节内容投影到连续高维向量空间，通过余弦相似度度量概念距离；
   - 擅长捕获近义词、跨语言表述与模糊语义联想（例如搜索“换行异常”能够召回“CRLF 幽灵 Diff 治理”）。
3. **排序融合（RRF，Reciprocal Rank Fusion）**：
   - 检索时双轨并行召回，采用 RRF 公式（$score(d) = \sum \frac{1}{60 + rank_i(d)}$）综合加权排序，兼顾精确关键字与概念泛化召回。

### 问题 3：旁路清单（manifestFile）的具体物理结构与适用场景

#### 提问
> 告诉我 manifestFile 这个旁路清单文件具体的结构如何？

#### 回答
旁路清单专为**严禁直接修改正文的场景**设计（例如符号链接引入的只读技能库、第三方文档包）。在源 Markdown 文件保持逐字节不变的前提下，通过外部配置文件赋予其完整的一等公民血缘身份。

清单采用 YAML 格式，根节点为 `documents` 映射，以文件相对路径为键（对应 `packages/validator/src/config.ts` 中的 `ManifestDocument` 契约）：

```yaml
# mdlineage.manifest.yaml
documents:
  packages/validator/src/index.ts:
    id: code.validator.entry
    kind: reference
    status: active
    authority: canonical

  docs/架构设计/系统架构.md:
    schema: 1
    id: docs.architecture
    kind: architecture
    status: active
    authority: canonical
    topics:
      - system-architecture
      - derived-index
    relations:
      - type: depends_on
        target: docs.vision
        reason: 架构设计落地愿景中确立的四项核心支柱。
        evidence: "#product-pillars"
```

当某篇文档的正文中已显式编写了 Front Matter 时，系统优先采用 Front Matter，并对清单中的重复条目发出 `MDL105` 告警。

### 问题 4：第三阶段环境实体与事实探针、AST 语法树与 4 项本地命令详解

#### 提问
> 我对于第三阶段“环境实体与事实探针探测”不太明白，具体原理如何？AST 又是什么？你提到的本地探针，这四个命令又是什么？which、--version、test -e、nc，这些不依赖大模型的功能，你需要给我详细解读。

#### 回答
1. **解决的根本痛点**：
   文档中经常记录外部物理环境事实（如“构建依赖 Node >= 20”、“服务监听 5432 端口”、“二进制位于 `/usr/bin/mdlineage`”）。文档文本本身未被修改，但外部环境发生软件升级、卸载或端口冲突时，文档陈述的事实便会静默失效。
2. **AST（抽象语法树）是什么**：
   AST 是将纯文本 Markdown 解析成计算机可直接遍历的树状数据结构。Markdown 被分类为具体的语义节点：`Heading`（标题）、`Code`（代码块）、`InlineCode`（行内代码）、`Link`（链接）。探针无需盲目全文正则扫描，而是精准过滤 `Code` 和 `InlineCode` 节点，提取其中的命令、文件路径与端口。
3. **4 项本地探针命令执行原理**：
   - **`which <binary>`**：在操作系统环境变量 `$PATH` 中检索指定可执行程序。退出码 0 表示命令已安装，非 0 表示外部工具依赖缺失；
   - **`<binary> --version`**：调用工具的版本输出参数，读取标准输出文本，提取语义化版本号（SemVer，如 `v24.16.0`），与文档声称的版本范围（如 `>= 20.0.0`）进行区间比对；
   - **`test -e <path>`**：POSIX Shell 内置的文件系统存在性测试（`-e` 表示 exists）。直接验证文档提及的物理路径或配置文件是否在磁盘真实存在；
   - **`nc -z <host> <port>`**：Netcat 网络探测工具（`-z` 表示 Zero-I/O 模式）。仅发起底层 TCP/UDP 握手探测目标端口连接性，用于验证文档记录的数据库或服务是否处于监听存活状态。
