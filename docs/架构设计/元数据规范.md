# Front Matter 元数据规范草案

本文档定义 MDLineage Markdown 文档的前置元数据（Front Matter）契约。数据模式遵循严格的精简原则，所有字段均由底层 JSON Schema 提供类型保障。

## 范例

```yaml
---
mdlineage:
  schema: 1
  id: docs.cache-policy
  kind: policy
  status: active
  authority: canonical
  topics:
    - caching
    - security
  aliases:
    - cache TTL
    - 缓存有效期
  relations:
    - type: depends_on
      target: docs.authentication-model
      reason: 缓存键包含账户身份与权限作用域范围。
      evidence: "#cache-key"
---
```

反向关系由被引用方在其自身文档中按需声明，禁止在此处就地冗余反向字段——反向引用由派生索引自动计算生成：

```yaml
# 在 docs/high-risk-account-policy.md 中声明
relations:
  - type: refines
    target: docs.cache-policy
    reason: 高风险账户采用更短的缓存有效期。
    evidence: "#high-risk-accounts"
```

## 字段语义定义

- `schema`（必填）：元数据 Schema 版本号。v1 规范目前仅接受数值 `1`。
- `id`（必填）：全仓全局唯一且稳定的逻辑文档标识符。当文件物理路径移动或重命名时，ID 保持不变。
- `kind`（必填）：文档类型，取值受词汇表约束，默认涵盖 policy（策略）、guide（指南）、architecture（架构）、reference（参考）等。
- `status`（必填）：文档生命周期状态，如 draft（草稿）、active（现行）、deprecated（已废弃）、archived（已归档）。
- `authority`（可选）：权威级别标定，如 canonical（权威基准）或 supporting（辅助参考）。
- `topics`（可选）：精炼的主题关键词列表，用于过滤和检索。
- `aliases`（可选）：搜索别名、缩写或中文/英文近义词。
- `relations`（可选）：已确认的强类型血缘关系数组。面向作者的实操指南见 [关系撰写指南.md](../使用手册/关系撰写指南.md)。
- `reason`：关系成立的简明理由说明。强影响关系（如 `depends_on`、`implements`、`refines`、`supersedes`、`contradicts`）强制要求非空理由。
- `evidence`：指向目标文档的标题定位锚点，形如 `"#anchor"`。锚点通过 GitHub 兼容的 GFM Slug 算法与目标文档标题对齐。若目标文档不存在该标题，由 `MDL402` 报告。面向作者的实操指南见 [关系撰写指南.md](../使用手册/关系撰写指南.md)。

## 基础关系词汇表

| 关系类型 (`type`) | 语义解释 | 是否驱动变更影响分析 |
|---|---|:---:|
| `depends_on` | 当前文档依赖目标文档中定义的规则、事实或契约 | 是 |
| `implements` | 当前文档记录了目标文档所提出设计的具体落地实现 | 是 |
| `refines` | 当前文档对目标文档的规则进行了细化约束或条件收窄 | 是 |
| `supersedes` | 当前文档替代了目标文档，成为现行有效的新指引 | 是 |
| `contradicts` | 两篇文档记录的主张存在不一致，标记为逻辑冲突 | 需人工复审 |
| `example_of` | 当前文档是目标概念的一个具体示例说明 | 通常不驱动 |
| `related_to` | 广义主题关联，无强依赖属性 | 否（仅用于探索发现） |

边的方向固定为单向语义 `A <type> B`。例如 `A depends_on B` 表达当 B 发生修改时，A 处于受影响波及集合中。反向视角完全由派生索引生成。关系方向固定，不支持自定义每种关系的方向倒转。

## 核心规则

1. **ID 全仓唯一且稳定**：`id` 取值必须在全代码仓内唯一，并在文件移动时保持恒定。
2. **目标唯一反解**：每个 relation 的 `target` 必须能够严格反解到恰好一个已知的文档 ID（由 `MDL302` 守门）。
3. **强关系强制理由**：强影响关系类型必须携带非空且有实质意义的 `reason`（由 `MDL102` 与 `MDL304` 守门）。
4. **只存储正向单向边**：严禁在 Front Matter 中手写反向引用，所有入边反查交由索引派生层。
5. **正文超链接作为独立拓扑**：普通 Markdown 相对链接解析为 `links_to` 出边，与 `relations` 分层并存。
6. **严禁在 Front Matter 中混入派生噪音**：禁止持久化文本嵌入向量、正文哈希、置信度浮点数或自动生成的时序打点。
7. **模型生成建议保持隔离**：LLM 生成的关系提案在未经人工审阅确认前，不得直接落入权威 Front Matter。
8. **保留未知顶层字段**：读写更新文档时，完整保留其他外部工具可能写入的 Front Matter 字段，避免破坏其他生态。

## 提案生命周期

模型或算法推断出的候选血缘关系，必须包含以下结构后呈现在审阅队列中：

- 源文档与目标文档的逻辑 ID。
- 建议的关系类型（`type`）。
- 两端文档中抽取的文本证据与标题定位锚点。
- 置信度评分与简要推导依据。
- 分析模型标识、版本号与被分析内容的内容哈希。

初版提案一律生成可审阅的 TextEdit 补丁。仅针对主题词（topics）或别名（aliases）等低风险元数据，支持配置策略进行受控的自动合并。
