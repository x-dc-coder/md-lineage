# 目录规范与布局治理提案

状态：草案中，待进一步完善。本文档定义 MDLineage 的第四项核心支柱能力（P4）：针对 Markdown 知识库物理目录布局与文件组织的声明式治理规范。

## 痛点与背景

Markdown 知识库通常依赖物理目录划分文档类型，但缺乏刚性约束机制。随着多轮迭代，设计文档、会议记录、现行规范与临时报告极易混堆在一起；文档发生重定位后，关联元数据与超链接往往未同步调整；开发者和智能体无法再信任目录结构所表达的语义。与死链或重复 ID 不同，目录布局漂移往往是静默发生的。

典型问题场景：

- 正式设计文档滞留在仓库根目录，未及时收敛入受控的文档树。
- 文档的业务角色发生了演进（例如草案指南转正为权威策略），但未移动至对应类型要求的物理目录中。
- 特定目录内的文档逐渐偏离其预设用途，例如在 `docs/policies/` 目录下大量堆积操作操作手册。

## 演进方向

将物理目录布局视为声明式的仓库策略，通过 MDLineage 统一的校验引擎与配置文件进行门禁守门。在 `mdlineage.config.yaml` 中设立专属的 `layout:` 配置块：

```yaml
# mdlineage.config.yaml
layout:
  - match: docs/design/**
    require:
      kind: [architecture, reference]
      frontmatter: required
  - match: docs/policies/**
    require:
      kind: policy
      authority: canonical
    forbidStatus: [draft]
  - match: notes/**
    require:
      frontmatter: optional
```

目录布局校验由专用的 `MDL5xx` 诊断码区间进行守门。

该配置块同样遵循统一的 Schema 结构、诊断通信协议以及编辑器补全机制，能够编译为确定性的诊断码输出。

基于此构建的三项核心能力：

1. **路径与类别一致性 (Path–kind consistency)**：当仓库建立了物理目录与文档类型的映射关系后，文档 Front Matter 中的 `kind` 必须与所在物理目录相匹配，或在配置中显式登记为未过期的豁免项（`layoutExceptions`）。
2. **布局感知与移动重组建议 (Layout-aware suggestions)**：当检测到文档角色与物理位置脱节时，自动生成包含相对路径与元数据修正的移动提案。工具始终以提案方式展现，不发生静默移动。
3. **移动成本影响评估 (Move impact)**：在接受文档移动提案前，系统自动枚举所有引用该文档的入边关系、反向链接与标题锚点，使重构成本透明可见。

## 设计约束

- **按仓库灵活定制**：目录规范是按仓库可配置的策略。MDLineage 提供执行引擎与推荐默认规则，不硬编码单一死板的目录拓扑。
- **混合型代码仓兼容**：代码、文档与构建产物共存是工程常态，规则必须支持 Glob 匹配并兼容 `.gitignore` 规则。
- **全通道一致性**：检查在编辑器（LSP 实时响应）和 CI 命令行（全量刚性门禁）中表现完全一致。
- **赋能智能体导航**：智能体严重依赖物理路径反解定位文档，目录布局校验能够直接降低智能体迷航概率。

## 待决议问题

1. 目录规则应在文档创建时、移动时还是作为持续诊断项报告？持续报告对迁移过渡期的仓库可能存在噪音。
2. 当 Front Matter 缺失 `kind` 时，应以 Front Matter 为单一事实源，还是允许根据目录自动推断默认 `kind`？
3. 例外项的声明与过期机制（显式白名单、时效性豁免条款 `expires`、还是子目录规则覆盖）？
4. MDLineage 是否应直接落地执行移动操作（生成跨文件 WorkspaceEdit），还是仅提供报告供外部工具应用？
5. 诊断码区间规划：默认采用保留的 `MDL5xx` 策略区间，保留 `MDL7xx` 作为备选备用区间。
