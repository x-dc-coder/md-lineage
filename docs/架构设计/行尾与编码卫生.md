# 行尾换行符治理规范

本文档记录了曾影响本仓库的 CRLF 跨平台换行符故障、其背后的深层触发机制，以及将“换行符卫生治理”收敛为 MDLineage 核心产品能力的演进方案。本文档兼具故障事后复盘报告（Post-mortem）与产品特性规范的双重属性。

## 1. 历史故障复盘 (2026-09-21)

### 症状表现

仓库中有 6 个受版本控制的文件在未发生实质性改动的情况下被 Git 标记为已修改，且 diff 显示整篇内容被全部删除并重新添加：

```text
349 insertions(+), 349 deletions(-)  # 实际文字内容完全一致
```

执行 `git diff --ignore-cr-at-eol` 输出完全为空：整篇唯一的变动是每行行尾多出了一个不可见的 `\r` 字符。

### 证据链分析

| 证据项 | 解读依据 |
|---|---|
| `git ls-files --eol` 输出 `i/lf w/crlf` | 索引与 HEAD 提交中均为 LF；当前工作区（Worktree）中为 CRLF |
| 6 个文件的修改时间（mtime）均为克隆时点（16:56:49） | CRLF 产生于检出时刻，后续未发生二次修改 |
| `.git/config` 包含 `filemode = false` | 证明是由 Windows 侧的 Git 通过 `\\wsl.localhost` 网络路径写入；原生 WSL 克隆应为 `filemode = true` |
| Windows 侧 `git.exe` 全局配置为 `core.autocrlf=true`；WSL 侧未配置该参数 | 两套平台环境之间的 Git 配置存在不对称 |

### 事件时间线

1. 开发者在 Windows 侧通过 `git.exe` 将仓库克隆至 `\\wsl.localhost\...` 目录。在 `core.autocrlf=true` 的作用下，检出动作将所有文本文件的行尾重写为了 CRLF。由该途径提交的内容仍被规范化为 LF，因此远端提交历史保持干净。
2. 随后所有终端命令切换至 WSL 原生 Git 执行。WSL 侧 Git 不做自动转码，按字节逐一比对发现工作区 CRLF 与索引中的 LF 不一致，因此将所有文件全部报告为已修改——产生大面积幽灵 Diff。
3. 后续在 WSL 环境下新建的文件（如 `docs/remark-language-server-solution.md`）保持 LF 格式，最终导致工作区内出现混乱的混合换行符状态。

## 2. 根因剖析：为什么 WSL/Windows 双系统切换会引发该问题

`core.autocrlf` 参数控制检出与提交时的文本转换规则。下表展示了未配置 `.gitattributes` 时（即故障发生时的仓库初始状态）各环境的默认行为：

| 配置值 | 检出时转换 | 提交时转换 | 典型分布平台 |
|---|---|---|---|
| `true` | LF → CRLF | CRLF → LF | Git for Windows 安装程序默认选项 |
| `input` | 保持不变 | CRLF → LF | 推荐用于标准 Linux 开发环境 |
| 未设置 (unset) | 保持不变 | 保持不变 | WSL 原生环境默认选项（按原始字节处理） |

一套 `.git` 元数据目录与一份工作区被两个操作系统平台同时共享，各自运行独立的 Git 运行时与独立配置。当 Windows 侧执行写入（autocrlf 自动转换）而 WSL 侧执行状态读取时，每个换行符都会被识别为 Diff。反之，若 Windows 侧配置为 `autocrlf=false` 配合默认 CRLF 的文本编辑器，极易将 CRLF 混入版本历史中。反复交替触碰同一批文件会导致行尾在不同平台间来回翻转，污染代码审查、破坏基于变更集（`--changed`）的工具链，并彻底打乱 `git blame` 归属追溯。仅靠对齐单机配置（如要求所有机器配置 `input`）极不可靠：配置容易漂移且不会随仓库分发，换一台机器便会重现故障。唯有在仓库中显式提交版本化的属性规则，才能保证策略伴随代码一同分发。

## 3. 仓库级修复方案（已应用）

提交版本化的 `.gitattributes` 能够覆盖所有机器本地的 autocrlf 配置，并随代码克隆自动生效：

```bash
printf '* text=auto eol=lf\n' > .gitattributes
git add .gitattributes
git add --renormalize .     # 强制按新规则对所有文本文件重新计算哈希
git checkout-index -f -a    # 根据索引重写工作区文件（统一收敛为 LF）
```

操作细节说明：`git checkout-index` 仅在判定工作区副本需要刷新时才会执行写盘。其跳过判定基于文件元信息（stat）——若文件的缓存状态（mtime、size）与索引记录吻合，则判定为未改动并予以跳过，此时 `-f` 亦无法强制覆盖。在此次故障中，CRLF 文件与索引哈希不同，因而被成功重写；若存在因元数据恰好巧合而被跳过的情况，先删除该工作区文件再重新执行 `checkout-index -f -a` 即可强制重写。验证结果：执行 `git ls-files --eol` 显示全量文件均为 `i/lf w/lf`，`git status` 恢复整洁。

推荐工程协作准则：

- 统一在单一系统边界内操作 Markdown（例如使用 VS Code WSL 远程扩展，统一调用 WSL 侧 Git）。
- 将 Windows 侧全局的 `core.autocrlf` 显式设为 `false`，将权威控制权完全交由 `.gitattributes`。

## 4. 产品化演进：将换行符卫生作为 MDLineage 核心能力

仓库级修补仅能保护当前特定仓库，且依赖协作者自律。MDLineage 将换行符健康度作为文档健康的核心支柱（P3），分三层实现产品化：

### 4.1 探测层 (Detection)

在统一校验规则栈中接入行尾检测能力：

- 诊断码 `MDL601`：单文档内部存在混合换行符（如同时包含 LF 与 CRLF）。
- 诊断码 `MDL602`：文件换行风格与仓库声明策略不符（默认策略为 LF，可配置）。

执行切入点：在语法树 AST 解析之前，与 Front Matter 边界扫描器并列，对原始文本 Buffer 执行高速轻量扫描。即使底层 Markdown 语法损坏无法解析，行尾检测依然能够精准运行，并实时响应未保存的编辑器缓冲区。在命令行批量模式中，`check --changed` 直接扫描工作区原始字节（或借助 `git status --porcelain`），而不依赖 `git diff`——因为在生效的 `text=auto eol=lf` 规则下，纯 CRLF 变动不会产生 git diff 输出，基于 diff 的判定会发生静默漏报。

### 4.2 修复层 (Repair)

- 提供安全无副作用的自动修复能力，将换行符整篇标准化至目标策略。全文本 EOL 转换不会改变注释结构与字段顺序，符合“安全自动修复”的标准。
- 多修复规则执行时序：结构性修复（Front Matter / AST 补全）优先计算，行尾规格化最后执行，并在规格化过程中动态重算各 TextEdit 的字节偏移量，保障位置映射有效。
- CLI 命令：`mdlineage fix --write` 将换行符治理纳入默认安全修复项。

### 4.3 预防层 (Prevention)

- 提供脚手架模板引导：`mdlineage init` 会在缺失属性配置时自动生成包含 `* text=auto eol=lf` 的 `.gitattributes` 文件。若已存在，则仅输出只读 diff 并安全追加缺失规则，不破坏已有内容。
- `mdlineage check` 在检测到工作区文本与声明策略背离时发出告警，在提交入库与 CI 触发前提前拦截幽灵 Diff。
- CI 持续集成门禁：流水线中验证 `.gitattributes` 存在并覆盖 Markdown 路径，且提交对象内严禁包含 CRLF 字符，形成多道防线。

### 4.4 非目标 (Non-goals)

- 不在声明策略之外静默篡改或重写用户文件。
- 不强制修改用户的全局系统级 Git 环境变量；MDLineage 负责声明并执行仓库级契约。

## 5. 验收完成定义

- 建立覆盖 CRLF、LF、混合换行及纯 CR 文件的测试用例，`MDL601`/`MDL602` 诊断表现稳定。
- 安全修复能够在单次 TextEdit 中将混合文件收敛至标准策略，语义与语法树保持不变。
- `mdlineage check --changed` 能够精准捕获纯换行符漂移并输出稳定的机器可读诊断码。
- 自动化测试套件中包含针对幽灵 Diff 的端到端复现验证用例。
