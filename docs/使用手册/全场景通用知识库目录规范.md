# 全场景通用知识库目录规范

本规范为多轮复杂迭代的软件工程、科研算法与跨平台项目提供统一的 Markdown 知识库目录结构与治理规则。规范采用**全中文目录与中文文件命名**，面向终端开发者提供清晰直观的信息架构，并通过 MDLineage 的声明式目录意图契约（`layout.intent`）实行机器级质量守门。

相关文档：[`使用指南.md`](./使用指南.md)（快速入门与功能全景）、[`配置指南.md`](./配置指南.md)（配置文件参考）、[`系统架构.md`](../specs/architecture.md)（架构设计）。

## 1. 设计背景与核心痛点

大型复杂仓库（如跨系统工具链系统 `Words-Production`、算法科研与分支演进系统 `M-PCA`）在经历多次重构与版本迭代后，文档通常呈现四大典型问题：

1. **现行基准与过程草稿混杂**：带有日期的临时讨论稿（如 `方案-2026-09-17.md`、`修改稿_v2.md`）与现行架构设计混堆，新接入的开发者无法分辨权威事实源。
2. **面向用户与内部审查混杂**：面向最终用户的配置指南与提供给大模型/子代理审查的测试报告（如 `P0三次复审与真机验证.md`）平铺在一起，增加阅读噪音。
3. **顶层目录无序扩散**：仓库根目录下散落着 `reports/`、`archive/`、`初稿/` 等平级文件夹，缺乏统一的文档索引入口。
4. **命名风格割裂**：数字前缀、时间戳前缀、英文连字符与中文混合，分类边界模糊。

## 2. 总体架构：五大核心骨架与领域插槽元模型

规范采用“**5 个通用核心骨架 + 1 个领域特化插槽（Domain Slot）**”的分层模型。所有文档统一收敛于 `文档/`（或仓库已有约定 `docs/`）之下：

```
docs/
├── README.md                      # [必需] 知识库全景地图与模块索引
│
├── ─── 通用核心骨架 (任何项目均具备，跨领域恒定) ───
├── 使用手册/                      # 【受众：外部消费者】现行指南、配置参考、故障速查 (纯中文)
│   ├── 使用指南.md                # 快速入门与端到端核心操作流程
│   ├── 配置指南.md                # 配置文件选项字典与环境变量说明
│   ├── 诊断码速查.md              # 错误码排错手册与修复建议
│   └── 命令行参考.md              # CLI 子命令语法与参数清单
│
├── 架构设计/                      # 【生命周期：现行基准】系统设计、契约协议与决策记录
│   ├── 系统架构.md                # 系统分层、核心模块与边界划分
│   ├── 元数据规范.md              # Front Matter 元数据与模式契约
│   ├── 目录契约设计.md            # P4 目录规范与重构引擎设计
│   ├── 统一语言服务设计.md        # LSP/MCP 统一方案设计
│   └── 行尾与编码卫生.md          # 换行符与文件编码策略
│
├── 迭代计划/                      # 【生命周期：进行中】项目规划、演进台账与生态分析
│   ├── 项目愿景.md                # 北极星指标与长期愿景
│   ├── 特性路线图.md              # 版本迭代路线与里程碑
│   ├── 进度台账.md                # 交付成果与演进过程台账
│   └── 开源生态分析.md            # 竞品对比与生态位分析
│
├── 质量审查/                      # 【受众：内部与模型】红队审查报告、审计波次与验收规范
│   └── 审查报告/                  # 大模型/子代理独立审查报告 (允许中英文)
│       ├── 2026-09-21-第一轮裁决报告.md
│       └── 2026-09-21-GLM独立审查报告.md
│
├── 历史归档/                      # 【生命周期：已封存】已结项成果、历史快照与废弃设计
│   └── 202608-早期重构方案/       # 按年月或模块封存的旧版文档
│
└── ─── 领域特化插槽 (按项目所属领域按需激活 1 个) ───
    └── [领域专属目录]/
```

### 2.1 领域插槽（Domain Slot）挂接规则

核心骨架保持跨项目一致，特殊领域的专属内容通过唯一的“领域插槽”承载，避免污染通用骨架：

| 项目领域 | 典型场景 | 激活的插槽名称 | 插槽承载的特化内容 |
|---|---|---|---|
| **算法研发与学术科研** | 如 `M-PCA` | **`研究实验/`** | 论文手稿、对比实验记录、消融分析、期刊审稿答复 |
| **工程软件与系统工具** | 如 `Words-Production` | **`工具链集成/`** | 跨系统桥接可行性、第三方内核调优、专用格式提取 |
| **数据科学与数仓工程** | 数据平台 / ETL | **`数据资产/`** | 数据血缘、指标定义字典、Pipeline 跑批监控报告 |
| **开源社区与商业产品** | 开源 SDK / 平台产品 | **`开源治理/`** | 贡献者指引、RFC 提案、用户协议、安全披露规范 |
| **多智能体协同系统** | Agent 农场 / 工作流 | **`智能体资产/`** | Prompt 提示词资产、Eval 评测集、角色卡规范 |

**插槽三项准入铁律**：
1. **不与核心骨架争抢语义**：若内容属于“现行的系统设计”，哪怕是数据结构也必须归入 `架构设计/`；领域插槽仅承载该领域专属的探索性或过程资产。
2. **生命周期出口统一**：任何领域插槽中的文档一旦结项、过期或废弃，统一迁移至 `历史归档/` 封存，禁止在插槽内部私设归档子文件夹。
3. **配置契约同步声明**：激活插槽时，须在 `mdlineage.config.yaml` 的 `layout:` 中声明其 `intent.kinds` 约束。

## 3. 命名与编码规范

### 3.1 路径与逻辑 ID 双轨制
为兼顾人脑直观阅读与机器图谱的引用稳定性，实行双轨制原则：
- **物理路径与文件名（给人看）**：采用清晰的**纯中文**，例如 `文档/使用手册/配置指南.md`。
- **元数据稳定 ID（给机器与图谱看）**：在 Front Matter 中显式声明标准的**小写 ASCII 稳定 ID**，例如 `id: docs.user-handbook.configuration`。
- **收益**：后续即便对目录或文件名进行文字润色，跨文档的血缘关系（`relations`）依然基于稳定的逻辑 ID 解析，避免破坏全局依赖网。

### 3.2 命名格式与字符集约束
- **面向用户的稳定文档**：采用纯中文主题词，不添加动态版本号或日期（例如 `快速入门.md`、`配置指南.md`）。单一主题始终保持单一事实源，演进差异通过 Git 版本控制追踪。
- **阶段性报告与审查记录**：必须携带时序前缀 `YYYY-MM-DD-`（例如 `2026-09-21-第一轮裁决报告.md`），明确标识其审查基准时点。
- **跨平台字符防御**：
  - 编码必须为 **UTF-8 NFC** 格式，避免 macOS NFD 产生跨平台字节漂移；
  - 文件名仅允许使用中文字符、英文字母、数字和连字符 `-`，**严禁包含空格、全角符号与特殊标点**。

## 4. 文档生命周期流转机制

文档在项目迭代中遵循明确的三态生命周期流转：

```
       [新建编写]
           │
           ▼
   [草稿期: 迭代计划/工作台/] (status: draft)
   ── 临时联调、POC 验证、问题排查、方案草案
           │
           │ (功能结项通过)
           ▼
   [现行期: 使用手册/ 或 架构设计/] (status: active, authority: canonical)
   ── 沉淀为现行正式指南或架构基准
           │
           │ (新方案替代或旧版本废弃)
           ▼
   [归档期: 历史归档/] (status: archived)
   ── 移入历史归档，切断活跃依赖，触发 MDL801 豁免
```

1. **两步状态机**：弃用旧文档时，先在原目录标记为 `status: deprecated`（给引用方提供迁移宽限期，由 `MDL306` 提醒下游迁移）；完成更替后，通过 `mdlineage move` 搬迁至 `历史归档/` 目录并标记为 `status: archived`。
2. **时效免检机制**：移入 `历史归档/` 的文档自动命中 `lifecycle.exempt` 规则，系统不再报告 `MDL801` 超期警告，切断维护负担。

## 5. MDLineage 自动合规检查配置

在仓库根目录的 `mdlineage.config.yaml` 中，配置对应的目录意图契约以硬性守门：

```yaml
configVersion: 1

metadata:
  required: true

vocabulary:
  kinds: [guide, reference, architecture, spec, policy, plan, report, vision]
  statuses: [draft, active, deprecated, archived]
  authorities: [canonical, supporting]

layout:
  - match: '**/*.md'
    require:
      frontmatter: optional
  - match: 'docs/**'
    require:
      frontmatter: required

  # 1. 使用手册：只允许指南与参考文档，禁止草稿
  - match: 'docs/使用手册/**'
    intent:
      description: '面向终端开发者的现行中文使用与配置手册'
      kinds: [guide, reference]
      forbidStatus: [draft]
      maxDepth: 2

  # 2. 架构设计：只允许架构与技术规范，强制 canonical
  - match: 'docs/架构设计/**'
    intent:
      description: '系统架构基准、数据模型与技术规范'
      kinds: [architecture, spec, policy]
      authority: [canonical]
      forbidStatus: [draft]

  # 3. 迭代计划：推进中的规划与台账
  - match: 'docs/迭代计划/**'
    intent:
      description: '推进中的阶段任务、路线图与台账'
      kinds: [plan, report, vision]

  # 4. 质量审查：存放审查与审计报告
  - match: 'docs/质量审查/**'
    intent:
      description: '审查与审计报告'
      kinds: [report]

  # 5. 历史归档：强制状态为 archived
  - match: 'docs/历史归档/**'
    intent:
      description: '已结项或废弃的历史档案'
      statuses: [archived]

lifecycle:
  staleAfterDays: 180
  staleStatuses: [active]
  exempt:
    - 'docs/历史归档/**'
```

## 6. 存量仓库渐进式治理流程

对于已有上百篇文档的存量复杂仓库，采用三步法平滑迁移：

1. **第一步（资产摸底）**：
   运行 `mdlineage organize --inventory` 查看全仓文档的类别分布与目录分布。
2. **第二步（安全重构与链接自愈）**：
   使用 `mdlineage move <src> <dst> --write` 逐一迁移文件，工具自动重写全仓所有受影响的相对链接、图片路径并保持锚点有效。
3. **第三步（基线保护与 CI 守门）**：
   运行 `mdlineage baseline update` 将未迁移的遗留债务登记进基线文件，在 CI 中启用 `mdlineage baseline verify` 与 `mdlineage check .`，确保后续开发不再产生新的目录错位。
